# v0.2 macOS 性能实测（阶段 6）

日期：2026-11-06。仅记录实际运行的结果；没有运行的项在第 7 节列出，不推断、不以目标值代替测量值。
v0.1 的测量记录在本地未发布的 v0.1-macos.md 中；本报告沿用其口径，并按 `docs/plans/v0.2.md` M10 第 2 条
新增三方合并、Blame 大文件、单文件历史长链的测量。

## 1. 环境与方法

| 项 | 值 |
| --- | --- |
| 机器 | Apple M2 Max，12 核，32 GB 内存 |
| 系统 | macOS 27.0（26A428），arm64 |
| 工具链 | rustc 1.99.1、Node 25.6.1、pnpm 12.16.1、Git 2.54.0（Apple Git-157） |
| 被测代码 | main `46924b9`（M0–M8 已提交） |
| 应用产物 | `pnpm tauri build --target universal-apple-darwin --bundles app,dmg`（universal，ad-hoc 签名） |
| 核心测量 | 临时 Rust 程序（`/tmp/gitwood-perf/bench`，未纳入仓库），release 构建，直接调用 `gitwood-core` 的会话 API 与真实 Git |

- **应用级**（第 3、4 节）：用独立 `HOME` 启动 universal 可执行文件，每次新建配置目录；
  启动 15 秒后按 5 秒窗口连续采样 60 秒。进程树为应用进程加启动后新增的 WebKit 助手进程，
  CPU 与内存经 `libproc`（`proc_pid_rusage`）读取，内存同时记录 footprint 与 RSS（口径说明同 v0.1）。
- **核心级**（第 5、6 节）：每个场景都新建仓库会话，不复用缓存；
  除另注明外每项运行 5 次，取中位数，并列出最小值和最大值。系统文件缓存未清理（`purge` 需要 root），因此是热缓存数据。
- 应用目前没有启动时自动打开仓库的入口，打开仓库需要在界面中操作；本轮没有辅助功能 / 屏幕录制权限，
  所以**应用级只测了欢迎页**，打开仓库后的场景只在核心级测量（见第 7 节）。

夹具（`/tmp/gitwood-fixtures/`，均不在源码仓库内）：

| 夹具 | 规模 | 用途 |
| --- | --- | --- |
| `graph-50k` | 50,001 提交 / 200 合并 / 10,001 文件（`scripts/make-fixture-repos.py` 生成） | 大仓库加载 |
| `perf-file-history` | 10,000 提交，每次改写同一个 20,000 行文件 `big.txt` 中的一行（轮转） | 单文件历史长链、Blame 大文件 |
| `perf-merge` | 20,000 行文件，两侧修改同一批区域，合并后 500 个冲突块，停在合并中 | 三方合并 |
| Gitwood 源码仓库 | main `46924b9` | 普通规模的真实仓库 |

`perf-file-history` 与 `perf-merge` 由临时脚本 `/tmp/gitwood-perf/make_v02_fixtures.py` 生成（fast-import / 真实 merge），
脚本未纳入仓库。

## 3. 空闲 CPU（欢迎页）

| 运行 | 平均 % | 峰值窗口 % | 采样窗口数 |
| --- | ---: | ---: | ---: |
| 1 | 2.53 | 17.44 | 12 |
| 2 | 0.23 | 0.83 | 12 |
| 3 | 0.25 | 1.14 | 12 |
| 4 | 0.02 | 0.13 | 12 |

- 4 次中 3 次 60 秒平均低于 1%；**第 1 次为 2.53%，超出目标**：第 8、9 个窗口出现 8.48% 与 17.44%，
  之后回落到 0.3% 以下。该次没有做按进程归属，来源未定位，也未能复现。
- 第 3、4 次加了按进程归属：超过 1% 的两个窗口（1.13%、1.14%）几乎全部来自 `gitwood` 进程本身（约 1.0%），
  WebKit 助手均低于 0.1%。欢迎页空闲时 `gitwood` 进程偶发约 1% 的活动，原因未定位。
- 打开仓库后的空闲 CPU 未测（见第 7 节）。

## 6. v0.2 新增场景（核心级）

### 6.1 单文件历史长链

`perf-file-history` 的 `big.txt`，10,000 个修订。

| 操作 | 中位数 ms | 最小 / 最大 |
| --- | ---: | ---: |
| `file_history_open`（读取全部 10,000 个修订） | 95.6 | 94.0 / 96.0 |
| `file_history_page(0..200)`（首屏 200 行） | < 0.1 | — |

进程峰值 RSS 30.0 MiB。打开后分页直接取内存中的结果，不再运行 Git。

### 6.2 Blame 大文件（Annotate）

同一文件，20,000 行、10,000 个修订；每项运行 3 次。

**首测（修复前，main `46924b9`）**：每个未缓存的 200 行页面单独运行一次 `git blame -L`。

| 操作 | 中位数 ms | 最小 / 最大 |
| --- | ---: | ---: |
| `annotate_open`（固定修订、读取文件历史与内容） | 120.5 | 118.3 / 121.6 |
| `annotate_page(0..200)`（首屏 200 行） | 5,802.1 | 5,753.6 / 5,828.3 |
| 后续 5 页（200..1200，依次请求） | 29,019.0 | 28,892.5 / 29,064.1 |

对照：直接运行 `git blame --porcelain -L 1,200` 用时 5.7 秒，`git blame --porcelain --incremental`（整个文件）用时 5.9 秒。
在长历史文件上，Git 不论行范围大小都要遍历几乎全部历史，每页成本接近整文件 Blame；按单页实测耗时计算（不是实测值），
看完 100 页约需 9–10 分钟。

**修复后（同日）**：`annotate_open` 启动一次固定修订的整文件 `--incremental` Blame，按输出流式填充行缓存，
页面请求等待所需范围填满（事件通知，不轮询）。

| 操作 | 中位数 ms | 最小 / 最大 |
| --- | ---: | ---: |
| `annotate_open` | 114.2 | 111.7 / 125.8 |
| `annotate_page(0..200)`（首屏，等待整文件 Blame 填满该范围） | 5,968.7 | 5,966.1 / 6,102.5 |
| 其余 99 页（200..20000，依次请求） | 3.0 | 2.5 / 23.7 |

进程峰值 RSS 49.9 MiB（修复前 39.2 MiB，只测了前 6 页）。看完整个文件从约 9–10 分钟（推算）降到约 6 秒（实测）。
首屏仍需约 6 秒：`--incremental` 按归属提交输出，首屏中由最早提交引入的行要到遍历接近结束时才出现，
这部分耗时来自 Git 本身（与整文件 Blame 相同）。

### 6.3 三方合并

`perf-merge` 的 `big.txt`：20,000 行，500 个冲突块。

| 操作 | 中位数 ms | 最小 / 最大 |
| --- | ---: | ---: |
| `conflict_content`（读取 base / ours / theirs 三个版本并计算合并块） | 236.9 | 236.1 / 237.9 |

进程峰值 RSS 14.1 MiB。合并编辑器在界面中的渲染与滚动未测（见第 7 节）。

## 7. 未执行项

以下项目需要界面操作或本机无法提供的权限，本轮未测，不写成通过：

- 应用打开仓库后的启动耗时、空闲 CPU、内存与 Git 子进程：没有启动时自动打开仓库的入口，
  驱动界面需要辅助功能权限；本轮未获得。
- 启动到欢迎页静置的耗时、首屏可见时间：本轮未测。
- 合并编辑器、Annotate 列、单文件历史对话框在 WebView 中的渲染、滚动与翻页耗时：需要界面操作。
- 长时间浏览（约 10 分钟）的内存曲线：同上。
- Intel Mac 与 Windows / Linux：未验证；本报告只覆盖 arm64 macOS 上的 universal 产物。

## 8. 结论

- **体积**：universal `.app` 20.8 MiB，超出 20 MiB 目标约 0.8 MiB。
- **内存**：欢迎页 footprint 合计 84.8–114.8 MiB，在 200 MiB 目标内；打开仓库后的场景未测。
- **空闲 CPU**：4 次中 3 次达标（0.02–0.25%），1 次 2.53% 未达标且来源未定位；`gitwood` 进程偶发约 1% 的活动，需要排查。
- **新增场景**：单文件历史（1 万修订 96 ms）、三方合并（2 万行 / 500 冲突块 237 ms）表现良好；
  Blame 原先在长历史大文件上按页重复运行整段历史（首屏 5.8 秒、看完整个文件推算约 9–10 分钟），
  已改为整文件一次流式 Blame：首屏约 6 秒（等于 Git 整文件 Blame 耗时），其余页面合计 3 ms。
- **发布**：v0.1 记录的 DMG 打包阻塞已消失，universal DMG 可直接生成。
